# Отчет по домашнему заданию №2: Marketplace API

## Общая информация

В рамках задания был спроектирован и реализован REST API для маркетплейса. Основной упор делался на подход **Contract First** (сначала OpenAPI, потом код), строгую типизацию и реализацию сложной бизнес-логики заказов.

Стек технологий:
- **Язык**: Python 3.10
- **Фреймворк**: FastAPI
- **База данных**: PostgreSQL (запуск через Docker Compose)
- **ORM**: SQLAlchemy (асинхронный драйвер `asyncpg`)
- **Миграции**: Flyway (автоматический накат SQL-скриптов при старте контейнера)
- **Валидация**: Pydantic (модели генерируются автоматически из OpenAPI)

---

## Реализация критериев

### 1. OpenAPI и проектирование (Contract First)
Спецификация лежит в `src/main/resources/openapi/openapi.yaml`.
Сначала я описал все эндпоинты, типы данных и ошибки в YAML-файле. Это позволило четко зафиксировать контракт до написания кода.
Для генерации Pydantic-моделей используется `datamodel-code-generator`. Это гарантирует, что код всегда соответствует документации.
Команда для генерации: `generate.bat` (или `make generate`).

### 2. База данных и миграции
Используется **PostgreSQL** в Docker-контейнере.
Чтобы избежать конфликтов с локальными базами, порт базы изменен на **5455**.
Миграции накатываются автоматически через **Flyway** при старте `docker-compose up`.
Структура БД:
- `users`: пользователи и роли.
- `products`: товары (с привязкой к продавцу `seller_id`).
- `orders` + `order_items`: заказы и позиции.
- `promo_codes`: промокоды.
- `user_operations`: журнал операций для rate limiting.

### 3. Архитектура приложения
Проект разбит на слои:
- `app/api`: роутеры и контроллеры (обработка HTTP-запросов).
- `app/models`: SQLAlchemy модели (работа с БД).
- `app/schemas`: Pydantic схемы (валидация данных, сгенерированы автоматически).
- `app/core`: конфигурация, безопасность, middleware.

### 4. Бизнес-логика заказов
Реализован сложный процесс создания заказа (`POST /orders`):
1. **Rate Limiting**: проверяется таблица `user_operations`, нельзя создавать заказы чаще чем раз в минуту.
2. **Активные заказы**: нельзя создать новый, если есть незавершенный старый.
3. **Проверка стока**: проверяется наличие товара на складе.
4. **Резервирование**: остатки списываются в той же транзакции.
5. **Фиксация цены**: цена товара копируется в `order_items` на момент покупки.
6. **Промокоды**: валидация срока действия, лимита использования и минимальной суммы заказа.

### 5. Авторизация и роли
Реализована JWT-авторизация (`access` + `refresh` токены).
Ролевая модель:
- **USER**: может просматривать товары, создавать заказы.
- **SELLER**: может управлять своими товарами, создавать промокоды.
- **ADMIN**: полный доступ.

Проверка прав делается через dependency `get_current_active_user` и проверку поля `role`.

### 6. Логирование
Написан middleware (`app/core/middleware.py`), который перехватывает каждый запрос и пишет лог в JSON-формате.
Логируются: `request_id`, метод, путь, статус ответа, время выполнения и `user_id`.
`X-Request-Id` пробрасывается в заголовки ответа для трейсинга.

## Инструкция по запуску (для проверки)

Я настроил проект так, чтобы он запускался одной командой, даже если порты 8000 и 5432 заняты.

1. **Запуск инфраструктуры (БД + миграции)**:
   ```bash
   docker-compose up -d
   ```
   *Ждем пару секунд, пока Flyway применит миграции.*

2. **Запуск приложения**:
   ```bash
   python run.py
   ```
   Сервер запустится на порту **8001** (http://127.0.0.1:8001).

3. **Тестирование**:
   Открыть Swagger UI: [http://127.0.0.1:8001/docs](http://127.0.0.1:8001/docs)

## E2E Сценарий для демонстрации

1. **Регистрация продавца**:
   - `POST /auth/register` -> role: `SELLER`
   - `POST /auth/login` -> копируем токен.
   - Авторизуемся в Swagger (кнопка Authorize).

2. **Создание товара**:
   - `POST /products` -> создаем "iPhone 15", цена 1000, сток 10.

3. **Регистрация покупателя**:
   - `POST /auth/register` -> role: `USER`
   - `POST /auth/login` -> берем новый токен.
   - Перезаходим в Swagger под покупателем.

4. **Оформление заказа**:
   - `POST /orders` -> покупаем 1 шт. товара.
   - Проверяем ответ: статус `CREATED`, цена зафиксирована.

5. **Проверка ограничений**:
   - Пробуем создать заказ еще раз сразу же -> получаем 429 (Rate Limit) или 409 (Active Order).

6. **Отмена заказа**:
   - `POST /orders/{id}/cancel` -> заказ отменяется, сток возвращается (было 9, стало 10).
